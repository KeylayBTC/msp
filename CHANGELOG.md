# Changelog — Multisig Session Protocol

Every normative change to the specification is dated here. Section numbers refer to `spec/msp-spec-v0.1-draft.md`. Earlier history (before the protocol had its own name) is summarized under the first entry.

**Release status.** v0.1-draft.2 was published on 2026-11-21 as the first public revision. Revisions are numbered `draft.N`; a revision that changes bytes on the wire says so, and implementations of different drafts are not expected to interoperate.

## v0.1-draft.2 — 2026-11-18 (wire-incompatible with draft.1)

Response to an external design and clarity review of draft.1 received 2026-11-18 and discussed the same day; the review, the author's response, and the reviewer's evaluation of the response are in the author's working files, and the one discussion that produced a recorded alternative is `spec/notes/forwarding-and-multikey-note-2026-11-18.md`. Two decisions by the author are recorded first; the rest is specification.

- **Decision: SAS before anything (§5.3, §6.6, §6.7, §6.8).** The reviewer showed that under draft.1 a setup session disclosed both account xpubs before the humans compared the SAS, so a party admitted under a leaked code could be caught but not un-told. The author accepted one additional concurrent message per setup session to fix it. `SAS_REVEAL` (type 9, body `{1: sas_nonce}`) is now the first encrypted message every participant sends, in both session kinds, as soon as it holds the other hello; nothing else is sent, and nothing received is acted on, until the participant's own user has confirmed the SAS. KEY_CONTRIBUTION field 4 (`sas_nonce`) is withdrawn and reserved; SAS_REVEAL field 2 (`participants`) is withdrawn and reserved. The SAS inputs and the §10.3 vector are unchanged. The Q1 security argument is restated for the new schedule in §6.8 and remains pending review.
- **Decision: scope (§1.3, §6.6, §10.4).** v0.1 sessions have two participants; setup creates two-key wallets (`n = 2`, `m` ∈ {1, 2}; a threshold of 1 must be displayed in words); signing works for any wallet both parties hold on BIP-48 paths, however it was created. Three-key setup is deferred to the group-session work, which gains a new precondition (Appendix B item 4(d): a membership mechanism that gives each participant the expected count before it reveals). The reviewer's proposal to build a three-key wallet from a chain of pairwise sessions with forwarded keys, and the D-15 option of several keys in one contribution, were considered and are recorded in `spec/notes/forwarding-and-multikey-note-2026-11-18.md`, not adopted.
- §6.8: **two freezes** replace draft.1's single freeze rule — membership at SAS_REVEAL, terms at acceptance of the one SESSION_INIT or PSBT_REQUEST after SAS confirmation — with separate sending and receiving rules. **Opening the ceremony:** exactly one participant sends the first ceremony message (SESSION_INIT or PSBT_REQUEST), which identifies the initiator and names the session kind; the hello and reveal carry neither. New ERROR/ABORT code `11 role_conflict`.
- §5.3: the draft.1 "key-change rule" ("ignore a different `pk` from the same transport peer") is withdrawn as unobservable by a client; the participant-count rule is the only membership rule, and any valid hello from a third key aborts. Nonce retention corrected: a participant keeps its own `r` until it has computed and confirmed the SAS. Hello delivery: one hello per complete binary WebSocket **message**.
- §4.2: guarantees restated per participant; "signature may have been sent" is a required distinct state; local completion establishes only what that participant verified. §4.3: residual trust list gains the signing-device screen; "distinct keys do not prove distinct custody."
- §6.6: `n = 2` and `m` ∈ {1, 2} enforced in v0.1; `network = 2` (signet) added; duplicate key material rejected by 33-byte compressed public key (D-21); terms freeze stated; consent display for threshold 1. **Pre-funding checkpoint** added after DESCRIPTOR_CONFIRM: own key and full first address verified on the signing device and compared between participants, with recorded outcomes *device-verified* / *software-only* / *not done*; "ready to fund" depends on it. SESSION_FINALIZE unchanged in bytes; `sas_confirmed` is now necessarily true.
- §6.6a: canonical-import rule for wallets created outside MSP (one supported template, exactly `/0/*` and `/1/*`, else refuse); test-spend success criterion (a verified partial signature from every key before finalization).
- §6.7: order of a signing session stated; **one request and one requester per session**, a different payment is a new session, counter gaps end the session as *incomplete*, no retransmission; PSBT_REQUEST gains required field `3: network`; check (a) reworded (a wallet both parties hold, by mutual hash check); checks (d) `SIGHASH_ALL` only and (e) input amounts required for the fee added; mandatory approval display (destinations in full, amounts, fee, on the trusted screen where there is one); requester checks on returned PSBTs; `txid` byte order pinned.
- §6.1, §6.3, §6.4, §6.9: header `re` present only on PSBT_RESPONSE, PSBT_COMBINE, and an ERROR about a message; ERROR body field 3 withdrawn; strict deterministic-CBOR decoding (duplicate keys, non-canonical forms, trailing bytes rejected); field 9 is ciphertext followed by the full 16-byte GCM tag; ordered receiver steps with silent drop of malformed or unauthenticated input and counter advance only after authentication.
- §5.2, §5.5: KDF agility no longer claimed (the rendezvous identifier depends on the KDF, so peers on different KDFs never meet); v0.1 pins `v = 1`, `kdf = 1`, AES-256-GCM; an incompatible hello produces a local notice, not a wire ERROR.
- §7.1: exact join (text message of 64 lowercase hex characters; `joined` / `full` / `invalid`); one item per complete binary message, 256 KiB after reassembly; the relay retains each member's hello while it is connected and replays the set to a later joiner. §7.3: `bridged` defined on KEY_CONTRIBUTION only; a signing bridge is a courier. §7.4: the metadata inventory fixed (hello fields and envelope headers are visible to the relay; it can tell setup from signing).
- §8.1: states reordered — VERIFIED (SAS confirmed) precedes CEREMONY; new REVEALED state. §8.3: the full list of state a rejoin requires. §8.4: outcomes *incomplete* and *unknown* defined.
- Abstract, §0, §1, §2, §4.1, §4.4, §9, §12, §14, A.6, A.7, Appendix B: stale claims swept — the SAS no longer "covers the descriptor" or "proves identical terms"; the relay sees hello fields and headers; MSP carries key expressions and PSBTs and generates the BSMS Round-2 file locally; A.6's "detects an interposer before any ceremony content" is true under this order and was false under draft.1; A.7's QR flow gains the reveal pass.
- A.1, A.2, A.4 (not part of v0.1 conformance): the A.1 bundle MAC under `K_code` is noted as a password verifier; A.2 states the three code-derived verifiers a PAKE profile must replace; A.4 ratchet given independent directional roots with deletion of `K_AB`.
- **Same-day corrections after the reviewer's consensus check of draft.2** (all within the two-client design; none changes a message format): §6.8 **hold rule** — a participant still awaiting its own user's SAS confirmation must authenticate and hold, in order, the one SESSION_INIT and one KEY_CONTRIBUTION (or one PSBT_REQUEST) the faster peer may lawfully have sent, and process them after "matches" (without this, two honest users aborted because one clicked first). §6.1/§6.8 — `note` allowed only where a body schema lists it (SESSION_INIT, KEY_CONTRIBUTION, PSBT_REQUEST); SAS_REVEAL is exactly `{1: sas_nonce}`; before confirmation no ERROR and no ABORT `detail` is sent, failures end locally first. §6.4/§6.5 — AES-256-GCM is the sole suite (the "MAY negotiate ChaCha20" sentence removed; bit 0 reserved); counters are **consecutive**, a gap after authentication ends the session *incomplete* with new code `12 counter_gap`. §6.7 — fee check (e) requires the amount of every input of the transaction, not only the signer's; requester checks distinguish *signatures collected* (threshold not met; combined partial PSBT, no `txid`) from *finalized*, require at least one new verified signature per requested input, and forbid a signer from finalizing in its response. §4.2/§6.7/§8.4 — outcome vocabulary made consistent (*incomplete* is this participant's exchange; the peer's use of sent messages is *known* or *unknown*); the global "no wallet for anyone" sentence replaced by the local guarantee. §5.3 — the first valid non-self key fills the empty peer slot before the third-key rule applies. §8.1 — finalization requires a **completed, matching** pre-funding check, not merely a recorded one. After the reviewer's confirmation of those fixes, two signing clarifications: §6.7(e) — every input amount must be *verified* from a matching previous transaction or a trusted lookup, since a `witness_utxo` amount is a claim and a signer's signature commits only to its own input's amount (the 2020 two-session fee attack is the reason own inputs are not exempt); Appendix B item 8 must budget the resulting PSBT size. §6.7 — a collected signature proves a new descriptor-key signature, not which cosigner signed; a UI may name a cosigner only against a key its wallet has labeled.
- `conformance-suite-spec-v0.1-draft.md` and the `msp-next` transcript still describe draft.1 and must be regenerated against this revision before either is evidence. The close-out fixtures the reviewer asked for are the right ones: one setup transcript where one user confirms first, one signing transcript against an imported wallet that needs a further session to reach quorum, and refusal cases for an extra field in a reveal, a counter gap, a missing input amount, and a disconnect just after signature release.

## v0.1-draft.1 — 2026-11-09

- **§5.3, §6.8 (2026-11-09): SAS commitment adopted, pending review.** The hello grows to 109 bytes with a 32-byte commitment `cm = SHA-256("MSP-V1-SAS-COMMIT" || pk || r)` to a fresh SAS nonce; the MAC covers it. The nonce is revealed in the sender's first encrypted message (new field `4: sas_nonce` in KEY_CONTRIBUTION; new message type `9 SAS_REVEAL` for signing-only sessions, carrying the participant list from the requester in n-party sessions). The SAS is now over `channel_id`, `n`, and every participant's `(pk || r)`; `descriptor_hash` is removed from it; the whole digest is reduced modulo 31^12. Freeze rule: a participant's view of the session is fixed at its first reveal. New ERROR code `10 commit_mismatch`. Rejoin re-sends the identical hello. §1.3, §14, A.6, A.7, Appendix B item 6, and `review-questions.md` Q1/Q2 updated. §10.2 and §10.3 vectors regenerated; `assembly.json` no longer carries SAS values. Rationale and adversarial check: `spec/notes/sas-commitment-study-2026-11-07.md`.
- §4.1 (2026-11-10): the malicious-initiator bullet now covers any malicious participant, drops the mechanism walkthrough in favor of section references, and no longer says the SAS binds the descriptor (it has not since 2026-11-09). Editorial; no wire or conformance change.
- §6.7 (2026-11-08): mandatory signer validation gains check (c): outputs marked as the wallet's must derive from the finalized descriptor at the stated path (the change-address attack); bridges must pass derivation fields through intact.

- Front matter for publication: preamble, abstract, §0 motivation, §1.3 limitations, §4.4 prior and related work; §14 replaced by the divergence table against Keylay app v0.9.1.
- §1.1: asynchronous sessions declared the version-2 target; v0.1 decisions taken so as not to foreclose them.
- §6.1: message identity `mid` made deterministic — derived from channel, sender key, message type, and a per-(sender, type) round — so a resend carries the same identity; a conflicting body under one identity aborts with new ERROR code 9 `identity_conflict` (§6.9).
- §6.6: `derivation_template` restricted to the BIP-48 forms `m/48'/C'/A'/S'` with `C` and `S` tied to `network` and `script_type`; closes Appendix B item 5.
- §6.6, §6.6a: `script_type = 1` (P2TR) reserved and rejected in v0.1; closes Appendix B item 5a.
- §6.6a: comparison of the first address *as shown by the signing device* raised from SHOULD to MUST where the device displays one.
- §4.3: the web origin serving a browser client added as a residual trust item.
- §13: the protocol is published under its own name so other implementations can carry it without a product name.
- Appendix B: items 7 (per-transport metadata tables, §7.4) and 8 (payload-size budget against QR capacity, §7.3) added.

### History before the first public draft (2026-08-29 → 2026-10-08)

- 2026-10-08: hello changed to a fixed-width 80-byte string with a 48-byte MAC input (then 77/45 after the version-free magic `MSP-HELLO`); §5.3 processing order made normative; §6.8 comparison channel, procedure, and participant-count display made normative; the SAS security claim corrected (no commitment phase → offline collision search, Appendix B item 6); client-side participant cap; A.6 asynchronous comparison changed to the full first address; KEY_CONTRIBUTION carries a plain key expression (signed BSMS Round-1 record removed); SLIP-132 keys normalized to xpub/tpub before assembly; "verify on the signing device" rule; Appendix A.7 signing-device profile; §10.4 first address corrected.
- 2026-10-07: protocol named Multisig Session Protocol (MSP); domain-separation strings `KEYLAY-V1-*` → `MSP-V1-*`; all §10 values recomputed.
- 2026-10-06: symmetric descriptor assembly — KEY_CONTRIBUTION is broadcast and every participant assembles the descriptor locally (§6.6a); DESCRIPTOR_CONFIRM; the SAS binds `descriptor_hash`.
- 2026-10-04: code stretching changed to PBKDF2-HMAC-SHA512 to match the shipped app; §10.1 and §10.3 recomputed.
- 2026-08-29: first complete draft (as "Keylay Protocol").
